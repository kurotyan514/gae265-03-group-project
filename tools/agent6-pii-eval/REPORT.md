# 6 號文件辨識：照片個資能不能不送雲端？可行性實測

實測日期：2026-11-05。回應 Leon 的問題：「PII 真的不能用嗎？有沒有替代方案？」

## 結論

1. **Azure Language 的 PII 偵測可以用，但解決不了這個問題。** 它支援繁中（`zh-hant`），可是只處理文字，要先 OCR；原圖在 OCR 那一步就已經送出去了。
2. **有替代方案：本機先把圖上的個資塗黑，再把遮過的圖送 Azure 讀（方案 B）。** 用這批資料實測：
   - 遮過的圖送進 Azure 後，91 個個資欄位**沒有任何一個被讀出來**（唯一一次警示，人工確認是評分誤判）。
   - 非個資欄位仍讀得到 99%（400/405），關鍵欄位沒有被誤遮。
   - 這樣 ADR-0009「個資先在程式內去識別化才送雲端」**可以維持**，ADR-0022「原圖送 Azure 是例外」的那段可以拿掉。
3. **不建議只用本機 OCR（方案 C）。** 本機和 Azure 的整體讀取率一樣（都是 97%），但本機在一份清楚的收據上，把金額 **99999 讀成 66666，信心度還是 1.0**。這種讀錯沒有任何警訊，違反 ADR-0004 的精神（數字不能錯）。Azure 讀對了，關鍵欄位也是 34/34 全對。
4. **建議的流程：本機遮、Azure 讀、兩邊數字對不上就交給使用者確認。**
   1. 本機 OCR 找出個資位置並塗黑。
   2. 遮過的圖送 Azure 讀欄位。
   3. 金額、日期等數字，Azure 讀到的值和本機讀到的值比對；不一致就回「不確定」。
   4. 本機找不到應該存在的姓名（可能遮不到），就不送出，回「不確定」。這是失敗時的安全預設。

**還不能直接宣稱的事**：遮蔽規則是看同一批資料調出來的，要用另一批沒看過的樣本驗證，確認仍然 0 次漏遮，才能寫進 ADR 定案。

## 測了什麼

- 資料：`agent6_dataset_v1`，全部是虛構的合成文件。照片與沒有文字層的 PDF 共 63 份，A／B／C 三種品質，中、英、日三種語言。電子 PDF 只拿來校正比對規則（128/128 全部讀到）。
- 本機 OCR：RapidOCR，比較了 PP-OCRv4 和 **PP-OCRv6 多語模型**（簡繁日英），都不連網。比對時先用 OpenCC 統一簡繁。
- 雲端：Azure Document Intelligence `prebuilt-read`，免費層，訓練訂閱裡的「文件智慧」資源。原圖和遮過的圖各送一次。
- 方案 B 的遮蔽規則**不看答案**，只用三種線索：
  - 個資標籤旁邊的值（多語、容許 OCR 讀錯一兩個字）
  - 格式像個資的字串（沿用 `deidentify.py`）
  - 平台本來就知道的值（事件事實裡的姓名、帳號 email）

### 方案 B：遮蔽結果（PP-OCRv6 找個資）

| | 本機重讀遮過的圖 | **Azure 讀遮過的圖** |
|---|---|---|
| 個資欄位仍讀得到（共 91 個） | 0（誤判 1） | **0（誤判 1）** |
| 非個資欄位仍讀得到 | 99% | 99%（400/405） |
| 關鍵欄位被誤遮 | 0 | 0 |

那 1 次誤判：A6-065 的證號 `TEST-LICENCE-A` 和標題「Driving Licence」字樣相近，被評分規則當成沒遮掉。我直接檢查 Azure 回傳的全文，裡面沒有這個證號。

用 PP-OCRv4 找個資時，漏遮有 5 次，原因都是 OCR 把標籤讀錯（例如「保険番号」讀成「保番号」）。**所以方案 B 的安全性取決於本機 OCR 的品質**，要用 v6 這個等級的模型。

## 另外發現的事（6 號實作要注意）

- **個資的範圍要重新定義。** 「原文件識別」「遺失物品」的值是護照號碼（`TEST-PASSPORT-A`），不在 ADR-0009 列的範圍內，也沒有被遮到。
- **信心度不可靠。** 本機讀錯金額時，信心度是 1.0；答案標為「看不清楚」的欄位，本機也有 4 次照樣讀出原值。數字欄位要靠兩個引擎互相比對，不能只看信心度。
- **規則是看同一批資料調整的。** 需要另一批沒看過的樣本驗證。
- **速度是在 Mac 上量的。** 正式環境是 CPU 的 VM，要再量一次。PP-OCRv6 模型約 20 MB，`onnxruntime` 已經在專案的依賴裡。
- **Azure 免費層有速率限制**，連查詢結果都算次數。正式環境要用付費層（S0），或是排隊處理。費用與區域要寫進 ADR-0022。
