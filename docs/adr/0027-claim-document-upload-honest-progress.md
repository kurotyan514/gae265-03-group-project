# 理賠文件上傳的進度只顯示真實的結果：先加預覽與不確定進度，不串流、也不重播假階段

理賠頁（2-3）上傳框的「處理清單」現在只發一次同步的 `POST /incidents/{id}/documents`，同時等一個 600ms 的計時器，回應回來後才用計時器把「讀取內容 → 對應待辦 → 檢查規則」三步重播到結果。這個動畫不是 agent 真的做到哪一步；而且畫面是三步，GLOSSARY 的**文件辨識**是四件事（多了「存到使用者的理賠資料夾」）。想讓使用者感覺小助理正在處理他的文件，但畫面不能說出與事實不符的話：例如動畫已經打了勾的「存到 Drive」，實際可能存檔失敗，旅客會以為文件保存了。

先做前端的改善，並量真實耗時，再決定要不要做真的串流。名詞見 GLOSSARY 的**小助理**、**處理清單**、**處理階段**。

- **預覽**：圖片（JPG／PNG）在瀏覽器用 `createObjectURL` 顯示縮圖，點開可放大；PDF 與 iPhone 的 HEIC 顯示圖示加檔名與大小（不引入 pdf.js）。縮圖放在每一份的處理列，離開頁面就釋放（`revokeObjectURL`），重新整理後不保留，也不從 Drive 讀回。
- **等待中**（11/13 起改為逐步亮起三步驟，見「2026-11-13 設計者修訂」）：不重播假的逐階段動畫，只顯示不確定進度「小助理正在處理這份文件…」；超過 8 秒加上「照片需要久一點，請稍候」。排在後面的檔案標「等待中」。開啟「減少動態」時不轉圈，只顯示文字；處理列用 `aria-live="polite"`。
- **結果**：回應回來後，先顯示摘要「這次上傳 N 份：x 份已自動打勾、…」與「看全部 N 份明細」。**預設只列沒通過的文件，合格的折疊在「看全部明細」裡**（展開後按鈕變「收合明細」）；**只有不合格的有紅字**（不合格、無法辨識、辨識失敗、沒有完成），「需要你確認」是琥珀色，合格的是綠色。這是設計者 11/11 的要求，沿用互動原型（上傳框 `upBox`）的行為。**合格但帶提醒的（通過、追加、還缺另一份都可能帶）不折疊**，琥珀色、預設列出，標籤加「（有提醒）」並多一行提醒文字，摘要把提醒數寫在各類別的括號裡（規格書 v3.8 7.3.7 的範例：「6 份已自動打勾（其中 1 份有提醒）」），三種都算；沒有提醒的「追加」與「還缺另一份」維持折疊（設計者 11/11 確認，#305）。
- **處理階段不顯示**（設計者 11/11；結果裡不顯示這點仍有效，原因裡不再寫停在哪、有沒有存到 Drive 的部分已於 11/13 取消）：四個處理階段（認出文件種類 → 對應待辦 → 檢查內容 → 存到你的 Google Drive）原本降級成每列一行的階段小圖示，設計者決定跑完就不留在畫面上：沒通過的列在「檔名＋標籤」下只有一行紅字原因，原因裡已寫明停在哪、有沒有存到 Google Drive（「檔案未保留」「沒有存到你的 Google Drive」）、下一步。沒有授權或存檔失敗是「沒有完成」而不是「通過」，「不確定」在有授權時已先存成暫存檔；這些仍由 `Recognition` 的內容與「有沒有存放位置」推得，只是不再畫成階段。
- **不顯示輸入與輸出**：不像 `/dev/document` 攤開 OCR 文字、去識別化文字與規則比對的欄位值；只顯示結果標籤與原因（契約本來就規定 `reason` 不可含文件內容與個資，ADR-0009）。
- **依序處理**：多份檔案維持一份一份送。
- **逾時與錯誤**：不設前端逾時中止。網路中斷時，背景重新讀取事件，用待辦與檔案清單判斷有沒有進去：進去了就照常顯示結果；沒有才在那一列只寫「連線中斷，上傳失敗」（設計者 11/11，原本多說明「可能已經處理好了」，改成只寫這句）。不用「上傳失敗」直接結束的原因是伺服器可能已處理完，那樣旅客會重傳而產生重複檔案。
- **範圍**：只做理賠文件上傳（2-3）。2-1 的保單上傳是程式規則加方案比對，不是 agent，不加動畫（不暗示有 agent 在做事）。
- **用語**：對使用者一律稱「小助理」，不出現 agent、辨識、OCR。
- **量測**：上傳路由記 `document_recognize_ms`（毫秒、狀態、檔案類型與大小區間；不記檔名與內容），由 6 號在真 Azure 的環境收集。
- **流程**：先在 `/dev/ui` 做原型，設計者同意文案與畫面後，才改正式畫面。設計者已於 11/11 看過真實畫面並全部同意（#291：第一輪調整後，第二輪 B、D、E、F 可以，C 維持「有提醒的合格結果預設列出」），狀態改為 `accepted`。

## Considered Options

- **真的串流階段事件**（SSE 或輪詢）：使用者看得到 agent 真的做到哪一步。但 `recognize()` 要多一個進度回呼（6 號契約升版）、正式 API 要改成串流、6 號的 agent 要送事件，影響面大，而且現在沒有耗時數據證明有必要。暫不採用，見「何時重新評估」。傳輸方式可參考 [ADR-0007](0007-ingest-agent-sse-progress.md)。
- **保留現在的重播動畫**：好看，但會說謊，尤其是「存到 Drive」那一步。不採用。
- **像 `/dev/document` 一樣顯示每一步的真實輸入與輸出**：輸入輸出含個資，與 `reason` 不可含文件內容的規則衝突。不採用。
- **多份檔案同時處理**：看起來較快，但每份辨識會讀事件裡「已經通過的文件種類」（例如機票和登機證兩份到齊才勾待辦），同時送會互相看不到對方的結果；Azure Document Intelligence 也可能有速率限制。不採用。
- **重新整理後仍顯示縮圖（從 Drive 讀回）**：要多一條讀 Drive 的路徑，還要處理授權與去識別化；[ADR-0021](0021-claim-documents-in-user-google-drive.md) 的做法是原檔只在使用者的 Drive，平台不重新讀取。不採用。

## 2026-11-13 設計者修訂

設計者看過實際畫面後調整兩件事，**取代**上面「等待中」「處理階段不顯示」中對應的部分：

- **處理中改回顯示三步驟**：「讀取內容 → 對應待辦 → 檢查規則」逐步亮起（已過的打勾、目前這步轉圈），最短 2 秒演完，每份只演一次、結果出來後不重演也不留在畫面上。伺服器沒在 2 秒內回來時停在最後一步轉圈等結果；開啟「減少動態」時不轉圈，目前這步改實心圓點；超過 8 秒仍追加「照片需要久一點，請稍候」。不再顯示「小助理正在處理這份文件…」。三步是示意，不代表小助理真的做到哪；為了不說出與事實不符的話，沒有「存到 Google Drive」這一步，有沒有保存只由結果標籤（「檔案未保留」「沒有存到你的 Google Drive」）說明。
- **失敗訊息不重複資訊**：紅字原因不再寫「停在「對應待辦」」這類階段（原因本身已說明），也不再寫「這份沒有存到你的 Google Drive」（標籤已有「檔案未保留」）。例：選了「都不是」只顯示「你選了「都不是」，這份檔案沒有保留」。

## 何時重新評估真的串流

收集至少 30 份真實上傳後，若 **p95 超過 8 秒，或有超過兩成的請求超過 5 秒**，就另開票評估真的串流；屆時要動 6 號契約（升版並寫進 `docs/agents/handoff/contract-changelog.md`），並取代本 ADR。

## Consequences

- 結果的呈現以設計者 11/11 的要求為準（合格的折疊、只有不合格的有紅字）；上傳回應要多一個 `stored`（有沒有存到 Drive）才推得出標籤與紅字原因裡的「檔案未保留」「沒有存到你的 Google Drive」，只改平台的回應模型，不改 6 號契約與資料表。
- 2-3 處理清單與設計稿 v3.7 不同：取代重播動畫、加縮圖、處理中改成不確定進度、處理完不顯示處理階段、文案用「小助理」。設計者 11/11 兩輪確認後定案。
- 不動契約、不動 API；後端只加一行耗時日誌。
- 等待中沒有逐步動畫，感受比較單調；以誠實為先。
- 縮圖只活在這次上傳的畫面，重新整理後待辦列只剩檔名與份數，與現況一致。
