# 條文入庫前逐條做內容驗證，沒通過的停在切塊階段等人工決定

條款切成條文之後、算向量之前，程式逐條檢查條文是否與原始 PDF 的文字一致（流程圖的「2」，名詞見 [GLOSSARY.md](../../GLOSSARY.md) 的**內容驗證**）。通過的條文照常算向量入庫；沒通過的成為**待確認條文**，停在切塊階段，由管理者逐條決定刪除、修改文字或放行。入庫後再做**檢索自檢**，確認條文真的檢索得到。

承接 [ADR-0007](0007-ingest-agent-sse-progress.md) 的上傳 agent 與 `needs_review`，但把「整份工作全有或全無」改成逐條。目前只有單一險種上傳走這條路；合訂本上傳（拆分清單、逐險種驗證）還沒做，見 [#95](https://github.com/kurotyan514/gae265-03-group-project/issues/95)、[#96](https://github.com/kurotyan514/gae265-03-group-project/issues/96)。

## 流程

1. 切條文後，程式做內容驗證：原本 `validate.py` 的結構檢查，加上用兩套 PDF 工具（pymupdf、pdfplumber）建立標準答案、逐條比對的檢查（完整性、正確性、邊界、歸屬、長條文、可追溯性）。兩套工具讀法一致才當標準答案。每條的結果是通過、確定錯誤、需人工查看（工具不確定）或無法驗證；無法驗證不算通過。
2. 程式自動修復（丟掉空條文、排除超出範圍的條號、重複條號只留內容最長的一條）後再驗證一次，次數是設定（`INGEST_VERIFY_PASSES`）。
3. 仍是「工具不確定」的條文交給 LLM 確認，次數是設定（`INGEST_VERIFY_LLM_PASSES`，0 = 不用）。只有兩套工具讀法不同的類型會送；過長之類的提醒不是 LLM 能判斷的事，不送。**LLM 只能放行這一類，不能放行「確定錯誤」，也不改條文**，只看文字不看頁面圖片，理由、供應商與模型記在事件。
4. 通過的條文算向量入庫；沒通過的進入待確認條文，每條有自己的狀態（待處理、已放行、已刪除）。管理者修改文字後放行，視為已確認，不再重新驗證；舊字、新字與原因記在事件紀錄。
5. 入庫後做**檢索自檢**：每一條用標題加第一句在該險種內檢索，前 N 名找得到自己算通過。單條沒通過只標警告；險種的通過率低於門檻時標示檢索品質異常。N 與門檻是設定（`INGEST_SELFCHECK_TOP_N`、`INGEST_SELFCHECK_MIN_PASS_RATE`）。結果存在上傳工作的結果欄位，險種 API 回報待處理條文數與最近一次自檢。

驗證時各公司的 PDF 版面差異（欄數、標題寫法、頁尾行）用設定檔 `verify_profiles.toml` 描述，不寫進程式。

## Considered Options

- **入庫後才驗證**：能測到真的檢索得到，但壞資料已經在檢索裡，要能回復。採用的做法是兩層都做，內容驗證放在入庫前，檢索自檢放在入庫後。
- **LLM 判定驗證結果**：判定無法重現，也無法量誤報率與漏抓率。採用的做法是判定用程式，LLM 只處理程式自己不確定的一類。
- **LLM 改條文，或產生切塊策略後重切（[#18](https://github.com/kurotyan514/gae265-03-group-project/issues/18)）**：違反「條文一個字都不改」的原則，且 LLM 可能把數字改錯（[ADR-0004](0004-llm-never-produces-numbers.md)）。這一階段不做。
- **維持 PR #33 的獨立工具，由 backend 呼叫**：多維護一個環境，而且它抓資料用的 `GET /rules` 只在非 production 存在。採用的做法是把檢查邏輯搬進 `backend/app/ingest/verify/`，保留「驗證用自己的切段規則，不沿用 backend 的切塊程式」的原則，避免用同一套邏輯檢查自己。
- **整份全有或全無（ADR-0007 現狀）**：一條有問題整份都進不了庫。採用逐條。
- **勘誤另建資料表**：正式環境的後端容器沒有持久的檔案空間，執行時寫入的資料只能放資料庫，所以勘誤原本需要資料表。但這一期管理者修改只需要稽核，不需要驗證器自動套用，所以舊字、新字與原因先記在事件紀錄，不建資料表；repo 裡既有的 `clause_errata.json` 維持唯讀。之後要讓驗證器自動套用管理者的勘誤，再建表。

## Consequences

- 待確認條文沿用 `ingest_job.pending_rules` 這個既有的 JSON 欄位，每條多一個狀態，**不需要 migration**。
- 一個險種可能只有部分條文入庫（部分入庫只新增或更新通過的條文，不刪險種裡其他條文；舊版裡不在這次上傳的條文會殘留，直到管理者另行處理）。問答這一期不向使用者提示，但檢索時該險種若有待處理條文會寫 log（只記險種與條數，不記問題內容），險種 API 回報待處理條文數。
- 管理者權限這一期不做：等 Google 登入（[ADR-0020](0020-google-login-and-incremental-authorization.md)）接上後台，有登入就能用。[ADR-0016](0016-admin-writable-backoffice-and-plan-owned-insurances.md) 的 `ADMIN_EMAILS`（[#47](https://github.com/kurotyan514/gae265-03-group-project/issues/47)）不再是前置條件，是否仍要做另行決定。目前處理待確認條文的畫面只在非 production 的 `/dev/ingest`。
- 內容驗證的誤報率與漏抓率還沒量（[#97](https://github.com/kurotyan514/gae265-03-group-project/issues/97)，人工標準答案約 30 條）。先開啟擋下功能：誤報只增加人工確認的工作量；量完才把驗證結果標為「可信」。
- 險種從頁面中間才開始的合訂本，目前以整頁為範圍驗證會誤判（鄰近險種的文字被算進標準答案）；需要拆分清單提供險種起點的行位置，等 #95、#96。
- 檢索自檢的預設值（前 3 名、0.95）用真實條款量過一次（Azure `text-embedding-3-large`）：675/700 條通過，38 個險種中 7 個低於門檻（都是 40 條以上的大險種）。預設值是否合適，要看失敗條文後再決定。
- 需要新增相依套件 `pdfplumber`（`pymupdf` 已有）。
- 驗證與檢索自檢的結果要註明 LLM 與向量的供應商（開發用 Azure 的 gpt-4.1-mini 與原型的 Ollama 不可直接比較）。
