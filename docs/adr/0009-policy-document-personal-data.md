# 保單文件的個資處理：先去識別化再入庫，v1 不保存原檔

保單文件含姓名、身分證字號、保單號碼等個資，使用者上傳後要能跟 agent 對話。所有文字在送進 embedding、LLM 與 log 之前，先由程式規則去識別化；伺服器 v1 不保存原檔，只存去識別後的保單段落與向量。原檔日後存在使用者自己的 Google Drive（先建議，不實作）。

- **去識別化用程式規則，不用 LLM**：正規表示式加欄位標籤（例如「被保險人：」後面的內容），遮蔽姓名、身分證字號、保單號碼、電話、email、地址。理由是個資不能先送給 LLM 才被遮蔽，與 [ADR-0004](0004-llm-never-produces-numbers.md) 把 LLM 擋在確定性資料之外的精神一致。
- **原檔 v1 不落地**：後端在記憶體裡處理完就丟棄。`policy` 表保留可為空的 `storage_provider`、`storage_ref`，給日後存進 Google Drive 用；那需要 `drive.file` scope（見 [ADR-0008](0008-google-oauth-cookie-session.md)），要另外評估 Google 的審核。
- **使用者輸入與保單內容不寫進 log。**
- **刪除**：使用者可刪單份保單文件，或「刪除我的所有資料」，連帶保單段落、向量、對話與理賠案件（外鍵 `ON DELETE CASCADE`）。
- **不做自動過期**：沒有排程服務（[ADR-0003](0003-no-background-worker-yet.md)），v1 只有手動刪除，記為已知限制。

## Considered Options

- **伺服器保存原檔**（原型的做法）：使用者能回頭看，但要有檔案儲存空間、清除機制，也把個資集中在我們的伺服器。
- **用 LLM 去識別化**：能抓到沒有標籤的姓名，但個資會先送到雲端供應商。
- **程式規則 + 不保存原檔**（採用）：個資不離開後端記憶體，代價是漏網的欄位（見下）。

## Consequences

- 沒有緊鄰標籤的姓名、規則沒涵蓋的欄位，可能漏遮蔽。這是已知限制，驗收用構造的假個資文件量測，漏洩必須為 0（只保證構造集）。
- 因為不留原檔，換 embedding 模型時只能用已存的去識別文字重算向量，無法重新抽取原文。
- 理賠文件（流程圖的 6）也含個資，同樣要走這份規則；細節由 6 的負責人實作時補。
