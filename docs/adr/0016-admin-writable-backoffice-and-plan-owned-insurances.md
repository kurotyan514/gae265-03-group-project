# 後台可寫入，以管理者名單保護；險種屬於方案、各存一份；合訂本的拆解由人確認

營運者要在後台新增方案與條款，不能再靠手改 repo 裡的設定檔。這份決定取代 [ADR-0006](0006-insurance-agent-migration-decisions.md) 的 D7（後台第一版唯讀），並調整 [ADR-0014](0014-clause-bundles-and-nine-plans.md) 的做法。**這份只記決定與順序，實作還沒開始。**

## 後台的新增流程

1. 在後台選擇**方案**（公司只是方案上的文字屬性，不是獨立的一層）。
2. 在方案下新增**險種**，來源有兩種，由使用者在介面選擇，決定不同的拆解策略：
   - **單一險種 PDF**：走現有的上傳工作（判斷、切塊、驗證、人工確認，[ADR-0007](0007-ingest-agent-sse-progress.md)）。
   - **合訂本**：兩步。**分析**（同步、很快、不用 LLM）：偵測每個「第一條重新開始」的位置，列出候選邊界與標題前幾行。**入庫**（背景工作加 SSE 進度，沿用上傳工作的事件機制）：使用者逐一確認、改名或標成不收、勾選要收的章、選填各章的保單代碼，確認後算向量入庫。
3. 確認後的邊界存成這份合訂本的拆分清單（資料庫），下次同一份直接沿用，取代手寫的 `clause_bundles.json`。[#18](https://github.com/kurotyan514/gae265-03-group-project/issues/18) 的 LLM 策略設定日後只是產生候選邊界的另一種方式。

第一階段只做**條款維護**；公司與方案暫時仍在 `config/plans.json`，之後再搬進後台。

## 決定

- **後台可以寫入**，取代 ADR-0006 D7。寫入端點一律要管理者身分，讀取端點維持原樣。
- **管理者以 `ADMIN_EMAILS` 名單判斷**（環境設定，逗號分隔，同 `ALLOWED_EMAILS` 的寫法）。**留空代表沒有人能寫入**（和 `ALLOWED_EMAILS` 留空代表不限相反：寫入的預設要最嚴）。`require_admin` 依賴只讀 `CurrentUser.email`。不用 `ADMIN_TOKEN`：共用密碼無法追蹤是誰改了條款，也無法單獨撤銷某個人，而登入機制已經現成。
- **登入由其他成員開發，現在的版本是暫用的**（commit 35fe179）。整合的接縫只有兩個：`current_user` 依賴繼續存在，回傳的使用者至少有 `id`（UUID）與 `email`；`user.id` 主鍵不變，因為保單、對話、事件都外鍵到它。`google_sub` 搬到結構圖的 `user_identities` 是登入負責人的 migration。管理者判斷只依賴 `email`，不受登入實作影響。
- **層級是 方案 → 險種**。「保險商品」一詞停用（已從名詞表移除）。險種**屬於一個方案**，基礎型與進階型就算背後條款相同，也各存一份**完整**的險種。方案涵蓋險種裡的哪幾章由方案決定，所以問答檢索仍要依方案的章過濾。
- **保單代碼放在險種的 `policy_codes` 欄位**（jsonb：章名 → 保單代碼，整份險種沒有章的用空字串當 key），取代全域的 `policy_codes.json`，不新增表。（讀取端已完成：保單比對只讀這個欄位；`config/policy_codes.json` 只剩 `make seed` 的初始資料，seed 只補上、不覆蓋後台填的。）概念上就是把結構圖 `clauses.code` 搬到險種上。同方案內代碼不重複，由匯入時檢查。
- **現有資料的轉換順序**：先做後台匯入流程，能用之後，再用同一套流程把九個方案各匯入一次，取代現有九個方案共用的 39 個險種。轉換前現有資料照常運作，問答與保單比對不受影響。

## Considered Options

- **維持唯讀，靠手改設定檔與 PDF**：不需要權限機制，但新增一家公司就要改 repo、寫錨點清單，營運者做不到。
- **寫入用 `ADMIN_TOKEN` 標頭**：實作最簡單，但共用密碼放在瀏覽器，沒有人可追蹤。
- **險種屬於公司、方案引用險種（共用一份）**：不重複儲存，但後台要處理「這些險種已存在」與章範圍的引用，方案之間會互相影響。
- **只存方案包含的章**：資料與方案內容一致，不用檢索過濾；但加購的章不在副本裡，基礎型升級成進階型要重新匯入。
- **保單代碼放新表 `plan_policy_codes`**：資料庫能擋重複，但多一張表；險種已經屬於方案，欄位就夠了。
- **照結構圖建 `clauses` 表（一列一個保障項目）**：和設計圖一致，但要改 5、6、7 號 agent 的契約（目前用「險種代碼加章名」表示保障）。日後仍可從現有資料自動產生，所以不是死路。

## Consequences

- 條文與向量約為現在的 **1.7 倍**（677 條變成 1154 條），條款勘誤要在每一份副本各套一次；換來方案之間完全獨立，刪除或修改一個方案不影響另一個。
- `insurance.code`、`insurance.name` 目前全域唯一，副本之間會衝突，要改成方案內唯一（或讓代碼帶方案前綴）。
- 本文取代 ADR-0014 中「險種可被多個方案共用」「章範圍存在 `plans.json`」「`policy_codes.json` 與 `clause_bundles.json` 放在 repo」的部分；實作完成之前，程式仍是 ADR-0014 的狀態。
- 問答檢索依方案的章過濾這項工作**沒有消失**，要另外做。
- 結構圖要請設計者確認的調整（拿掉 `insurers`、險種屬於方案並移除 `plan_products`、使用者與第三方登入、險種的保單代碼欄位）已放在給設計者的確認表 D 組。設計者不同意時，這份的對應部分要重新討論。
- 寫入端點是新的攻擊面：必須有「未登入 401、非管理者 403、管理者成功」的測試，且名單留空時全部拒絕。
