# 5 號 agent v1：流程與結論由程式決定，LLM 只負責聽懂與白話說明

5 號 agent（事件釐清、總結與問答）的第一個真實實作，範圍是 #128：單一事故「班機延誤」、富邦國外旅平險-進階型。延續 [ADR-0004](0004-llm-never-produces-numbers.md)（數字不由 LLM 產生）、[ADR-0009](0009-policy-document-personal-data.md)（去識別化）、[ADR-0011](0011-claim-flow-bounded-llm-judgement.md)（有界的 LLM 判斷）與 [ADR-0015](0015-agent-handoff-contracts.md)（agent 不寫資料庫、只回契約）。

## 決定

- **LangGraph 控制流程**：守門 → 聽懂 →（追問｜下結論）；問完之後的提問走問答。每輪從 `IncidentContext` 重建狀態，不存 checkpoint；問過幾次也從對話紀錄重建。
- **分工**：
  - Jev 只做相關性分類（related／unrelated／unsure）：無關回固定訊息、低信心反問，兩者都不記狀況；服務失敗就跳過並記錄（不記使用者內容）。
  - LLM 只從旅客的話取出欄位片段；格式不符（時間、日期、選項）的答案丟掉，由程式再問。
  - 必問欄位順序、追問、結論都由程式決定。結論依富邦第 21 條（延誤四小時以上）與第 22 條第五款（未搭第一班替代班機，不可抗力除外 → 資訊不足）判斷。
  - 問答用 `create_agent` 搭唯讀的條文檢索工具，只能依查到的原文回答；回答含原文沒有的數字就退回列出原文。
- **判斷規則只套用在富邦險種**：其他公司的保障一律回報「資訊不足」（目前只支援富邦條款判斷）。門檻與除外條件各公司不同，套錯規則比不判斷更危險。
- **問答的檢索範圍**：只用這次事故適用的那一章，加上同一險種的共同條款；查詢帶上事故名稱。整張保單一起查時，曾查到別項保障的颱風除外條文而答錯。
- **追問上限**：同一題問 3 次、整段 15 輪，還沒答的記為「不知道」，結論就不會是「可能適用」。
- **去識別化**：送出 Jev 與 LLM 前，個資值從事件描述、旅客說過的話與本輪訊息一起找，前文出現過的姓名也遮蔽。
- **額度**：不計算金額，每項保障附固定說明「方案所載額度，實際以保單為準」。

## Considered Options

- **LLM 判斷是否理賠**：彈性高，但結論可能隨措辭變動，違反 ADR-0004 與 ADR-0011。
- **整個對話交給一個 tool-calling agent**：追問順序與結束條件難以保證，測試只能看最終輸出。
- **判斷規則套用所有公司**：程式較簡單，但其他公司的保障可能被誤判為可能適用或不賠。
- **問答查整張保單**：實測會引用別章條文（FUBON04 第 28 條）回答班機延誤問題。

## 後續

- 延誤超過 24 小時、否定時數、問答帶入事件狀況：#133。
- 其他公司的判斷規則、其他事故類型：v2。
- 共用資料（事故目錄的文件、提醒、事故類型）以所有公司為前提，不以富邦為準修改。
