# 規格：平台配合 7 號的新送件流程

> 狀態：7 號整理給平台負責人的需求，等平台負責人有空時處理（之後開 issue 時套用 `ready-for-agent` 標籤）。
> 撰寫：7 號開發者，2026-11-06。
> 依據：`docs/specs/agent-7-package.md`（「送件流程」「寄送」「需要平台處理」）、ADR-0004、ADR-0015、ADR-0020、ADR-0021。
> 這份文件只寫「平台要改什麼」；7 號自己的部分已在 `feat/agent-7-package` 分支做好，畫面可以在 `/dev/package` 試（不用登入，Google 授權是模擬的）。

## 問題

7 號與前端已經照新的送件流程做好（使用者先選代寄或自己處理；代寄要在預覽頁把空格與收件者填完才能寄出；自己處理可以選擇建立 Gmail 草稿；三種結果都結案）。但正式網站還用不到，因為平台有三個地方跟不上：

1. **使用者填的內容到不了 7 號**：送件 API 只收收件人，後端會重新產生一次送件信，所以使用者在預覽頁填的「被保險人姓名」「保單號碼」「聯絡電話」等空格都會不見。7 號規定有空格的信不能寄出，因此**現在正式網站一封信都寄不出去**，也沒辦法用測試帳號手動驗證寄信。
2. **契約沒有「建立草稿」**：`SendResult` 只有 `sent`、`failed`，`send` 也沒辦法知道使用者要的是寄出還是建立草稿。
3. **只有寄出會結案，結案後也沒有鎖住**：使用者選「自己處理」時事件不會結案；結案後還是可以傳訊息、改待辦、上傳文件、再送件一次，可能寄出重複的信。

## 解法

- **送件 API 一次說清楚「要做什麼」**：使用者按下的是「寄出」「建立草稿」還是「自己處理、不建草稿」，連同填好的空格與收件者一起送給平台。平台把填好的值放進 7 號產生的信，再交給 7 號寄出或建立草稿；自己處理、不建草稿時不經過 7 號，平台直接記錄並結案。
- **契約 v2.1 加上「建立草稿」**：`send` 多一個「寄出或建立草稿」的選擇，`SendResult` 加 `drafted`。
- **三種結果都結案，結案後鎖住**：寄出、建立草稿、自己處理不建草稿都把事件標成完成；完成的事件不能再新增狀況或修改，也不能再送件。

## 使用者故事

1. 身為旅客，我想在預覽頁把「（請填寫＋項目）」填完後寄出，信上就是我填的內容，這樣保險公司收到的是完整的信。
2. 身為旅客，我想讓預覽頁看到的信和寄出的信一模一樣，這樣我確認過的內容不會在寄出時被換掉。
3. 身為旅客，我想在空格沒填完時寄不出去，並看到還缺哪幾項，這樣不會寄出有空格的信。

6. 身為旅客，我想選「我自己處理就好」後，讓系統在我的 Gmail 建立草稿，這樣我可以在 Gmail 修改後自己寄。

8. 身為旅客，我想在建立草稿時不一定要填收件者，這樣我可以到 Gmail 再填。
9. 身為旅客，我想選「我自己處理就好」並且不建立草稿時，事件也算處理完，這樣我的事件清單不會一直掛著這件事。
10. 身為旅客，我想在寄出、建立草稿、自己處理之後看到事件已結案，這樣我知道這件事處理完了。
11. 身為旅客，我想讓結案的事件不能再新增狀況或修改，這樣送出去的內容和系統裡的紀錄一致。
12. 身為旅客，我想在結案後重按送件時被擋下，這樣保險公司不會收到兩封一樣的信。
13. 身為旅客，我想在寄送失敗（沒授權、Drive 找不到附件、暫時連不上 Google）時事件不會結案，並看到原因，這樣我可以處理後再寄一次。
14. 身為旅客，我想在沒有授權 Gmail 或 Drive 時看到「請先授權」的說明，而不是看不懂的錯誤，這樣我知道下一步要做什麼。
15. 身為旅客，我想讓寄出的信用我自己的 Gmail 寄出，寄件者就是我，這樣保險公司的回覆會回到我的信箱。
16. 身為旅客，我想在正式網站的送件畫面看到和開發頁一樣的流程（先問代寄或自己處理、授權說明、預覽填空、寄出），這樣操作方式一致。
17. 身為平台負責人，我想讓送件紀錄照實記錄寄出（`sent`）、建立草稿（`drafted`）、自己處理（`self_submitted`），這樣之後查得到每個事件是怎麼結案的。
18. 身為平台負責人，我想讓 7 號仍然只回傳結果、不碰資料庫，送件紀錄與事件狀態由平台寫入（ADR-0015）。
19. 身為平台負責人，我想讓送件紀錄只存編號與狀態、不存使用者填的內容與信件內容，這樣符合個資規則（ADR-0009）。
20. 身為平台負責人，我想讓「空格寫成（請填寫＋項目）」這個固定寫法寫進交接說明，這樣平台、7 號、前端用同一個規則找空格。
21. 身為平台負責人，我想讓契約變更有預設值、舊的呼叫方式照樣能用，這樣假實作與其他測試不用一次全改。
22. 身為 7 號開發者，我想讓 `send` 收到的信已經填好使用者的值，這樣 7 號不用知道前端怎麼填。
23. 身為 7 號開發者，我想讓契約測試的整條流程給假授權、用填好的信寄出，這樣真的 7 號（離線版）跑得過整條流程。
24. 身為 6 號開發者，我想讓契約測試的整條流程給假授權，這樣真的 6 號上傳後能是 `recognized`。
25. 身為前端開發者，我想讓送件 API 在空格沒填完、收件者不對、事件已結案時回明確的錯誤代碼與訊息，這樣畫面能告訴使用者怎麼做。

## 實作決定

**送件 API**（`POST /incidents/{id}/submission`）
- 請求多兩個欄位（建議，平台可調整命名）：
  - `mode`：`"send"`（寄出）、`"draft"`（建立草稿）、`"self"`（自己處理、不建草稿）。不給時當 `"send"`，舊的呼叫方式照樣能用。
  - `fills`：「項目 → 使用者填的值」，例如 `{"被保險人姓名": "王小明", "保單號碼": "A123456789"}`。項目就是「（請填寫＋項目）」括號裡的文字。
  - `recipient`：`send` 必填，要是 email 格式；`draft` 可以不填；`self` 不用。
- 平台的處理順序：
  1. 檢查事件屬於這位使用者、還沒結案（已結案回 409「事件已結案，不能再送件」）。
  2. 檢查所有待辦都完成（現在就有，維持 409）。
  3. `self`：不呼叫 7 號，寫一筆 `self_submitted` 的送件紀錄，事件結案，回 201。
  4. 其他：呼叫 7 號 `build` 產生送件信，把 `fills` 放進空格。
  5. `send` 時，填完還有任何「（請填寫＋項目）」就回 409，訊息列出缺的項目，不呼叫 7 號。
  6. 呼叫 7 號 `send`，帶上填好的信、收件者與「寄出或建立草稿」。
  7. 依 7 號的結果寫送件紀錄、決定要不要結案（見下方「結案」）。
- **怎麼放進空格**：只換「（請填寫＋項目）」這一段，其他文字不動，使用者改不到程式產生的保額、日期等（ADR-0004）。值先去掉頭尾空白；空的值視同沒填，空格保留。`fills` 裡有信上沒有的項目時直接忽略，不回錯誤。
- **為什麼不讓前端直接送整封信**：前端只送「空格 → 值」，不送整封信，平台每次用 7 號重新產生、再放進值，使用者改不到其他文字，也不用信任前端送來的信件內容。
- 預覽仍用現在的 `GET /incidents/{id}/package`；前端在畫面上把值放進空格給使用者看，寄出時把同一份 `fills` 送給平台。前端與平台用同一個規則放值，畫面看到的就是寄出的。

**契約 v2.1**（`ClaimPackager`、`SendResult`）
- `send` 多一個參數 `mode: "send" | "draft"`，預設 `"send"`；`recipient` 在 `"draft"` 時可以是空值。（另一個做法是另開 `create_draft` 方法，請平台決定；7 號兩種都能配合。）
- `SendResult.status` 加 `"drafted"`；`external_ref` 在 `drafted` 時放草稿編號。
- 7 號的規則（已寫在 7 號規格「寄送」）：`"send"` 時信裡還有空格就回 `failed`；`"draft"` 時有空格也能建，空格在草稿裡醒目標出。
- 假實作（`FakeClaimPackager`）跟著支援 `"draft"`、回 `drafted`。

**送件紀錄與結案**
- 對照表：

  | 使用者的選擇 | 7 號的結果 | 送件紀錄的狀態 | 事件 |
  |---|---|---|---|
  | 寄出 | `sent` | `sent` | 結案 |
  | 自己處理、建立草稿 | `drafted` | `drafted` | 結案 |
  | 自己處理、不建草稿 | 不呼叫 7 號 | `self_submitted` | 結案 |
  | 寄出或建立草稿 | `failed` | `pending`（照現在的做法） | 不結案 |

- 資料表 `policy_submission.status` 已經有這四個值，不用改資料表結構；但 `drafted` 的說明現在寫「建了 Gmail 草稿，不結案」，要改成「結案」。
- `recipient` 的說明現在寫「建立草稿或寄出之前必須有值」，要改成「寄出之前必須有值；建立草稿可以沒有」。
- 送件紀錄只存編號與狀態，不存 `fills` 與信件內容（ADR-0009）。

**結案後鎖住**
- 事件結案（`status == "completed"`）後，下列 API 一律回 409「事件已結案，不能修改」：傳訊息、改待辦、上傳文件、確認文件、送件。
- 讀取類的 API（看事件、看送件包）照常可以用。
- 平台目前沒有任何結案後的檢查，這是新加的。

**契約測試**
- 整條流程（`test_full_flow_from_message_to_submission`）：給假授權（Drive、Gmail 都有），送件時帶 `fills`（被保險人姓名、保單號碼、聯絡電話）與收件者，預期 `sent`、事件結案（原本「需要平台處理」第 1 點的假授權一起做）。
- 另加劇本：沒授權時 6 回 `needs_review`、7 回 `failed`、事件不結案；建立草稿回 `drafted` 並結案；自己處理不建草稿記為 `self_submitted` 並結案；結案後再送件回 409。
- 6、7 號的契約測試改用各自的離線版跑（7 號是 `gmail-offline`，已註冊），不會真的連 Google。

**正式的送件畫面**（前端）
- 照 7 號規格「送件流程」做；可以直接用 `/dev/package` 用到的共用元件（送件信與空格輸入框、是否建立草稿的視窗）。
- 寄件者顯示使用者登入的 Gmail；收件者由使用者輸入。
- Google 授權用平台現有的授權說明視窗；正式頁面不要給開發頁專用的模擬授權設定。授權要整頁導向 Google，所以導回時要保留或還原使用者已填的值（例如先存在瀏覽器），避免填好的內容不見。

## 測試決定

- **好的測試只看對外行為**：從送件 API 打進去，檢查回應、資料庫裡的送件紀錄與事件狀態，以及 7 號（假實作）收到的信與參數；不測平台內部怎麼拆函式。
- **主要的測試接口只有一個：送件 API**。用假的 7 號記下「收到的信、收件者、寄出或建立草稿」，涵蓋：
  - `fills` 放進空格後交給 7 號；其他文字沒被改；空白的值不算填。
  - `send` 時還有空格回 409 且沒有呼叫 7 號；收件者不對回 422。
  - `draft` 沒有收件者也能建，回 `drafted`、事件結案。
  - `self` 不呼叫 7 號，記為 `self_submitted`、事件結案。
  - 7 號回 `failed` 時記為 `pending`、事件不結案。
  - 結案後再送件、傳訊息、改待辦、上傳文件、確認文件都回 409。
  - 不帶 `mode` 的舊呼叫方式照樣是寄出。
- **契約測試**：見上方「契約測試」，用 7 號離線版跑整條流程。
- **正式送件畫面**：照 `frontend/e2e/dev-package.spec.ts` 與 `frontend/e2e/google-dev-incident.spec.ts` 的寫法寫 e2e，不連 Google（ADR-0020）。
- **參考的既有測試**：`backend/tests/contracts/test_flow.py`（整條流程）、`backend/tests/contracts/test_v2.py`、`backend/tests/google/`（假的 Google 授權）、`backend/tests/agents/package/`（7 號自己的測試，含離線版）。
- **真的連 Google**：送件 API 改好後，由 7 號開發者用測試帳號手動寄一封給自己、建一封草稿，確認附件與內容（`docs/agents/handoff/google-login.md` 的驗證清單）。平台改完請通知 7 號開發者來驗收。

## 範圍外

- 7 號自己的實作：寄出已完成；建立草稿等契約 v2.1 定案後由 7 號接上。
- 整張保單送件（`build_for_policy`）、一次送件拆成多封信、附件大小（`size_bytes`）：照原本的 v2.1 規劃另外處理。
- 收件人資料表或自動帶入保險公司理賠信箱（ADR-0019）。
- 追蹤保險公司回信（ADR-0020 不請求 readonly 權限）。
- 結案後重新開啟事件。

## 其他說明（待決）

- **結案要鎖到哪一層**：送件紀錄（`policy_submission`）的說明寫「以保單為單位，一張保單底下所有事件一起寄出、一起結案」，但現在的送件 API 是以事件為單位。這份文件先照現在的 API，以事件為單位結案、鎖住；整張保單一起結案、結案後不能在這張保單新增事件，等 `build_for_policy` 一起定。
- **契約怎麼加「建立草稿」**：`send` 加 `mode` 參數，或另開 `create_draft` 方法，由平台決定。
- **錯誤代碼**：空格沒填完、已結案都用 409；收件者格式不對用 422（照 FastAPI 的驗證錯誤）。平台若有既定慣例，以平台為準。
- **API 欄位命名**（`mode`、`fills`）只是建議，平台可以改；改了請告訴 7 號與前端。
